UmaTools website and module audit

13 October 2026 · Working tree based on d2bdb73, including the pending master-data changes.

The website has a solid layout and baseline performance, but two issues should be fixed before the next release: executable markup in hint-share URLs and loss of saved event data during a provider outage. Recommendation accuracy, search state and keyboard dialogs also need attention. Targeted optimizations can improve responsiveness and reduce duplicated logic without changing the site architecture.

This audit made no application-code fixes or deployment changes. The production build ran in an isolated copy. Findings distinguish reproduced bugs, code-review risks and unresolved game-mechanics questions. The report covers all page entry points and the module groups below; it is not a claim of exhaustive game-formula verification or a penetration-test certification.

Prioritized findings

P1: fix before release. P2: correctness, reliability, accessibility or maintenance work to schedule next. P3: lower-impact portability issue. Security severity from dependency scanners is separately qualified.

P1 · F01 Hint URLs can execute JavaScript

public/js/hints.js:234,261

Confirmed in Chromium on the local site. URL-provided hint text flows through selected into innerHTML, including an unescaped attribute. A harmless image error handler set window.auditExecuted to 1. A shared link can therefore run code in the website origin and access its saved browser data. The live home response also had no Content-Security-Policy header; the exploit itself was tested only locally.

Recommended change: Build chips with textContent and DOM attribute setters; treat translations and hint strings as text. Add a regression test with markup and quotes in a shared URL. Introduce a compatible CSP as defense in depth after fixing the rendering sink.

P1 · F02 Provider failure can publish an empty event database

scripts/data/gametora.js:778,789,881; .github/workflows/gametora-scrape.yml:32

Confirmed by executing the real buildSupports function with a mocked training-event outage. It catches the failure, proceeds, writes [] to the support-event output, and returns normally with events: 0. The workflow sees success, so its rollback does not protect this case. Character-event loading has a similar catch-and-continue pattern. This can remove event answers during an upstream outage.

Recommended change: Build each dataset in staging; validate required inputs, nonempty outputs and acceptable count changes before atomic publication. Preserve prior event files when event extraction fails. Test each upstream failure separately, including successful card metadata with unavailable event data.

P2 · F03 Event recommendations ignore Wit rewards

public/js/recommend.js:248,259,295,326

Confirmed: scoreOption([["Wit +10"]]) returns 0, while "Wisdom +10" returns 8. The earlier parseRewardLine recognizes Wit, but scoreOption uses a second parser without that alias. The current character/support/career datasets contain 603 Wit reward lines (occurrences, not distinct events). Recommendations can consequently favor a weaker option. Additional synthetic cases expose Mood up/down scoring as zero and removal of Practice Poor status receiving a negative score; those exact forms were not found in the current corpus.

Recommended change: Normalize each reward into one typed representation and score that representation. Share alias, status and chance-outcome handling. Add corpus-based tests for all currently emitted reward formats and separate tests for synthetic edge cases.

P2 · F04 Event-search state can show an older answer or no answer

public/js/search.js:171,176,217

Both cases reproduced with local mocked API responses: a slow first search replaces the result of a faster second search; and searching a name, clearing the query, then searching the same name again leaves the result blank. LAST_QUERY_KEY outlives the visible result and there is no request ordering guard.

Recommended change: Use AbortController plus a request generation token before rendering. Reset the last-query state when clearing, or cache and re-render the actual payload. Test reverse response order, errors between successful searches, and clear/repeat.

P2 · F05 Optimizer work and memory scale with an unrestricted budget

public/optimizer.html:454; public/js/optimizer.js:4026,4055,5531; public/js/team-trials-optimizer.js:1328

The input has no maximum; the handler only rejects negative/NaN values. Both solvers size arrays from the budget. Calling the actual rating solver with 4,294,967,295 immediately throws RangeError: Invalid array length, without allocating a large array in this probe. More ordinary oversized budgets waste work on the main thread. A synthetic 50-skill case took about 114 ms at budget 5,000 and 670 ms at budget 30,000, producing the same 50 skills, 5,000 score and 5,000 cost.

Recommended change: Validate finite safe integers, then cap the internal DP budget at the maximum spend achievable across valid groups. Preserve the user-entered budget for remaining-points display. Test gold/lower/evolution groups, required skills, zero-cost entries and tie-breaking before changing storage or introducing a worker.

P2 · F06 Skill dialogs let keyboard focus escape behind the overlay

public/js/skill-popup.js:608,646,675

Confirmed in a local keyboard probe. The dialog declares aria-modal=true, but repeated Tab moves to BODY and then the background navigation. Closing does not restore focus to its trigger; anchorEl is unused. Static Lighthouse accessibility scores did not catch this interaction.

Recommended change: Use a native modal dialog where compatible, or add a focus trap, inert background and saved trigger focus. Verify forward/backward Tab, Escape, close button, nested skill links and opening the dialog from the skill browser.

P2 · F07 A malformed hint query throws during initialization

public/js/hints.js:234

Confirmed: /hints?hints=%25 produces URI malformed because URLSearchParams decoding is followed by another unchecked decodeURIComponent. Initialization fails at readFromURL; the requested filter is not restored even though other asynchronous content may still render.

Recommended change: Adopt one canonical encoding/decoding pass and tolerate malformed legacy links. Test literal percent signs, commas, Unicode, quotes and links generated by the current double-encoding writer before migrating.

P2 · F08 Event API does not bound its fuzzy-search inputs

api/[...path].py:439

Confirmed with FastAPI TestClient: limit=-1 returns HTTP 500; limit=0 returns 404; limit=100000 is accepted. An empty query with the large limit returns a match plus 1,872 alternatives. This is inconsistent with the newer master endpoint, which validates its query and pagination limits.

Recommended change: Require a nonblank, bounded event_name and a small positive bounded limit with FastAPI validation. Return 422 for invalid parameters; retain documented response behavior for valid searches. This is an input-validation and workload issue, not evidence of a production denial-of-service incident.

P2 · F09 Daily refresh omits generated race and derived skill updates

.github/workflows/gametora-scrape.yml:35,69; scripts/data/gametora.js:1192; package.json:25

The workflow runs --what all, which generates races.json, but its git add list omits races.json. A successful race refresh therefore remains on the disposable runner. The workflow also does not regenerate the GameWith CSVs or acceleration compatibility data. Calculator/optimizer ratings and acceleration data can stay behind even while the daily job succeeds. Code inspection confirmed these paths; no actual upstream freshness guarantee was inferred from timestamps.

Recommended change: Create an explicit output/dependency manifest. Stage all intended refresh outputs, regenerate dependent datasets, validate cross-file identities and counts, and publish them together. Give each dataset a visible source/version and last successful refresh.

P2 · F10 Provider jobs are not fully independent

.github/workflows/gametora-scrape.yml:42

The new master refresh is after Generate Skills Core, which has no continue-on-error or independent job. If that transform fails after a successful GameTora fetch, normal GitHub Actions step gating skips the master refresh and publication. The current failure-report step only covers the two provider steps. Thus the intended fallback isolation does not cover the complete pipeline.

Recommended change: Run each provider and its transforms in isolated staging/jobs and validate each result before merging outputs. Make partial-success and total-failure states explicit; retain prior assets for failed branches. Test generator failure as well as network failure.

P2 · F11 Build and audit dependencies have outstanding advisories

package.json; package-lock.json

npm audit reported 39 affected package entries: 17 high and 22 moderate, zero critical. The directly listed high-severity tools include lighthouse, postcss, puppeteer-core and sharp. These are development/build dependencies; npm audit --omit=dev reported zero. They are not proof of 39 independently exploitable browser vulnerabilities. Sharp processes image assets during the build and PostCSS parses project CSS, so untrusted build inputs are the relevant exposure.

Recommended change: Update dependencies in a controlled change, inspect upstream advisories, and rerun build, image checks and browser audits. Avoid a blanket forced audit fix: some suggested changes are major or involve downgrades. Python dependency advisories were not scanned; requirements are currently unpinned.

P2 · F12 Regression gates miss important behavior and are not enforced in CI

package.json:46,49; tests/unit/; scripts/audit/validate-data.js:34; .github/workflows/

The only checked-in workflow is the data scraper; no pull-request test workflow is defined. npm test/check omit test:master. validate-data checks JSON syntax/root type rather than schema, nonempty catalogs, CSV rating values or cross-dataset consistency. The API tests depend on httpx through TestClient, but it is not declared in requirements.txt. Existing responsive tests intentionally exclude API failures and do not exercise event searches, OCR recognition or recommendation accuracy. Several confirmed issues passed the existing gates.

Recommended change: Add a reproducible PR gate with explicit test dependencies, master-download tests, schemas and a small set of end-to-end regression scenarios for these findings. Keep expensive browser/performance audits separate or targeted. Add pure tests for recommendation parsing, rating solver reconstruction, acceleration/stamina boundaries and OCR matching fixtures.

P3 · F13 Guide validation falsely fails on Windows line endings

scripts/build/generate-guides.js:968,1026

npm run check stops at five guide SVGs. All five source/output pairs are identical after CRLF-to-LF normalization; source SVGs have CRLF and published copies have LF. This is a byte-comparison portability failure, not a visual defect. A complete build in an isolated copy succeeded and regenerated the five files.

Recommended change: Enforce a consistent .gitattributes policy for source and generated SVG/text assets, or normalize textual assets before comparison and writing. Verify fresh Windows and Linux checkouts. Do not keep rewriting identical diagrams as the remedy.

Data migration and aptitude rounding: still open

The new master API serves validated snapshots, but browser modules do not request it. Global CDN data is therefore not yet the primary source for calculators, optimizer or the skill library. Keeping the old consumers is not the same as implementing automatic API-to-provider fallback. A shared adapter needs to merge raw master ratings/costs with aliases, categories, skill chains and UI metadata, with explicit server and source tracking. JP is still a local import; no automatic current JP source has been verified.

The Studious row still contains base 85 and G-aptitude 59. JavaScript double precision evaluates 85 × 0.7 as 59.49999999999999; an explicitly rounded float32 product is 59.5. The current generator and multi-aptitude helper use ordinary Math.round. The numerical discrepancy is confirmed; exact game precision and midpoint behavior were not proven by this audit. Do not replace every rounding call blindly: include 85 × 0.7, 95 × 0.7, chained aptitude factors and midpoint tie behavior in game-backed reference tests.

Sources: public/assets/uma_skills.csv:331, scripts/data/gamewith-skills.js:581, public/js/rating-shared.js:121. Existing missing-server API behavior (503 rather than substituting Global for JP) is appropriate and should be preserved.

Recommended implementation order

  1. Fix hint URL injection and protect event datasets from partial provider failures; add focused regression tests first.
  2. Fix reward normalization, event-search sequencing, API bounds, malformed URLs and modal focus.
  3. Restore a portable, reproducible check pipeline; include downloader tests and refresh-output validation. Address dependency advisories in a separate tested update.
  4. Extract the shared skill repository and wire master snapshots into consumers with explicit legacy fallback and server provenance. Resolve aptitude precision with game-backed fixtures.
  5. Cap solver capacity, benchmark real builds, and defer full metadata. Only then consider workers or further payload splitting if interaction traces justify them.
